## Shell, navigation, and responsive behavior

- `DashboardDocument` is the shared Hono JSX/SSR shell. It places the brand, team switcher, a header account menu, layout-specific desktop navigation, the main landmark, and mobile navigation in one document ([apps/gateway/src/web/dashboard.tsx:80-118](../../../../../apps/gateway/src/web/dashboard.tsx:80)).
- Navigation is team-scoped and currently contains Overview, Artifacts, Projects, API tokens, Devices, and Team settings ([apps/gateway/src/web/dashboard.tsx:69-77](../../../../../apps/gateway/src/web/dashboard.tsx:69)). The `DashboardSection` union has no account or appearance section ([apps/gateway/src/web/dashboard.tsx:16](../../../../../apps/gateway/src/web/dashboard.tsx:16)).
- Sidebar, top navigation, and mobile navigation are separate renderers. Mobile renders only `items.slice(0, 4)`, while the sidebar is hidden at `max-width:820px`; the existing responsive CSS also hides the brand name, account copy, quiet link, and desktop sidebar at that breakpoint ([apps/gateway/src/web/dashboard.tsx:169-207](../../../../../apps/gateway/src/web/dashboard.tsx:169); [apps/gateway/src/web/dashboard-assets.ts:2](../../../../../apps/gateway/src/web/dashboard-assets.ts:2)). The implementation plan must preserve reachable account/theme controls when the sidebar is collapsed and when the mobile bottom navigation is present.
- The desktop sidebar has no collapse/expand trigger, persisted width, or resize interaction in the current markup/script. Its width is the fixed `--sidebar:236px`; it is sticky for the viewport and is replaced entirely by the mobile bar below 820px ([apps/gateway/src/web/dashboard-assets.ts:1-3](../../../../../apps/gateway/src/web/dashboard-assets.ts:1); [apps/gateway/src/web/dashboard.tsx:169-207](../../../../../apps/gateway/src/web/dashboard.tsx:169)). Any future collapse/resize slice must define keyboard semantics, reduced-motion behavior, persistence, and account-menu placement explicitly.
- The page shell loads one same-origin deferred asset for CSS and one for JavaScript ([apps/gateway/src/web/dashboard.tsx:84-93](../../../../../apps/gateway/src/web/dashboard.tsx:84); [apps/gateway/src/web/dashboard-routes.tsx:37-39](../../../../../apps/gateway/src/web/dashboard-routes.tsx:37)). The strict CSP allows same-origin scripts/styles and disallows inline script ([apps/gateway/src/web/http.ts:1-7](../../../../../apps/gateway/src/web/http.ts:1)).

## Theme behavior

- The shell hard-codes `color-scheme=dark` and a dark `theme-color` meta tag ([apps/gateway/src/web/dashboard.tsx:84-90](../../../../../apps/gateway/src/web/dashboard.tsx:84)). The device approval document repeats the same dark metadata ([apps/gateway/src/web/dashboard.tsx:744-750](../../../../../apps/gateway/src/web/dashboard.tsx:744)).
- Dashboard CSS defines only dark root tokens (`color-scheme:dark`, dark backgrounds, text, borders, and accent values) and includes many hard-coded dark colors in layout/component rules ([apps/gateway/src/web/dashboard-assets.ts:1-3](../../../../../apps/gateway/src/web/dashboard-assets.ts:1)). There is no light palette, theme data attribute, color preference media query, theme control, local-storage key, theme cookie, or system-preference listener in the dashboard source ([apps/gateway/src/web/dashboard-assets.ts:5-105](../../../../../apps/gateway/src/web/dashboard-assets.ts:5)).
- The shared dashboard script currently handles timezone cookie/reload, dialogs, copy feedback, confirmation prompts, refresh, and native `<details>` behavior. It synchronizes `aria-expanded`, closes details on outside click or Escape, and restores focus to the summary, but contains no theme state or persistence ([apps/gateway/src/web/dashboard-assets.ts:5-105](../../../../../apps/gateway/src/web/dashboard-assets.ts:5)).

## Account and authentication boundaries

- `AccountMenu` is a native `<details>` popover. Its trigger shows the session name/email and its content has the email, `Connect another device`, and a CSRF-protected `POST /auth/logout`; there is no account-page link or profile/appearance control ([apps/gateway/src/web/dashboard.tsx:148-167](../../../../../apps/gateway/src/web/dashboard.tsx:148)). The same component appears in the header and in the sidebar footer ([apps/gateway/src/web/dashboard.tsx:101-105](../../../../../apps/gateway/src/web/dashboard.tsx:101); [apps/gateway/src/web/dashboard.tsx:169-183](../../../../../apps/gateway/src/web/dashboard.tsx:169)).
- `WebIdentity` exposes only `id`, `email`, and `name`; `getWebSession` derives it from Better Auth only after requiring a verified email and a non-empty session token ([apps/gateway/src/auth/web-session.ts:5-25](../../../../../apps/gateway/src/auth/web-session.ts:5)). The D1 Better Auth user table also has `emailVerified`, `image`, timestamps, and account/provider/password records, but no dashboard profile helper currently reads or mutates those fields ([apps/gateway/src/db/schema.ts:13-75](../../../../../apps/gateway/src/db/schema.ts:13)).
- `requireDashboardSession` authenticates the browser session, loads memberships, resolves an optional team ID, and supplies role/layout/timezone context ([apps/gateway/src/web/dashboard-service.ts:25-32](../../../../../apps/gateway/src/web/dashboard-service.ts:25); [apps/gateway/src/web/dashboard-service.ts:104-121](../../../../../apps/gateway/src/web/dashboard-service.ts:104)). Team dashboard routes consistently call this helper through `dashboardSession`, which redirects 401 responses to login with a safe local return path ([apps/gateway/src/web/dashboard-routes.tsx:318-324](../../../../../apps/gateway/src/web/dashboard-routes.tsx:318)).
- Existing dashboard mutations use session-bound CSRF and reject foreign origins ([apps/gateway/src/web/dashboard-routes.tsx:81-113](../../../../../apps/gateway/src/web/dashboard-routes.tsx:81); [apps/gateway/src/auth/csrf.ts:23-34](../../../../../apps/gateway/src/auth/csrf.ts:23)). The account page should preserve this boundary and must not treat a team ID, role, or client-selected value as user authorization.
- Existing tests cover server-rendered sidebar/topnav/account-menu contracts, CSRF, sign-out forwarding, and auth/session behavior, but there is no account-page or theme contract test ([apps/gateway/test/dashboard.test.tsx:72-106](../../../../../apps/gateway/test/dashboard.test.tsx:72); [apps/gateway/test/auth.test.ts:270-376](../../../../../apps/gateway/test/auth.test.ts:270); [apps/gateway/test/dashboard-csrf.test.ts:1-40](../../../../../apps/gateway/test/dashboard-csrf.test.ts:1)).

These commands provide automated/source and packaging evidence; they do not establish authenticated browser, provider, system-theme, or deployed UI behavior.

## Proposed direction from target evidence

1. Keep the current SSR shell and native disclosure primitives. Add a user-scoped account route/page reached from the account menu, with profile/appearance scope only. Display only fields backed by the current session or a user-ID-scoped query; do not add passkeys, security integrations, billing, feedback, status, or unsupported mutations.
2. Add a small System/Light/Dark control informed by AIEO’s three-state row, but implement it as progressive enhancement under the target’s strict same-origin CSP. Decide persistence and first paint together: a server-readable theme cookie can seed `data-theme` before deferred JavaScript runs, while the script applies changes and updates the cookie; if local storage is retained, define a cookie/SSR fallback and a no-flash bootstrap explicitly.
3. Replace hard-coded dark-only assumptions with complete semantic tokens and light/dark/system behavior, including the approval page and native controls. Keep reduced-motion behavior and accessible focus/expanded-state handling for account/theme controls at desktop, topnav, sidebar, and mobile widths.
4. Preserve `/auth/logout` and the existing session/CSRF flow. Add route/render/service tests for the account page, theme markup and persistence contract, no-team/expired-session redirects, and both desktop/mobile shell variants; then validate with the discovered package/workflow commands and separately label runtime/deployed proof.
